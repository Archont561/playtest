# ADR 0016: Binary Distribution Channels for the CLI

## Status
Accepted (2026-11-11). Amends [ADR 0007](./0007-polyglot-monorepo-architecture.md) and [ADR 0008](./0008-two-phase-artifact-release-pipeline.md).

## Context

[ADR 0015](./0015-cli-first-distribution-and-five-crate-workspace.md) makes one Rust binary the version authority. That binary must reach repositories that install their tools with Pixi or conda, pip or uv, npm, pnpm or Bun, Go, R, or a plain download. Each registry has its own rules for executables.

The findings below were collected on 2026-11-11 from registry documentation and from experiments outside this repository. No repository test covers them yet.

- **npm.** A package that downloads its binary in a `postinstall` script does not work under Bun or pnpm, which skip the lifecycle scripts of dependencies by default. Per-platform packages listed as `optionalDependencies` need no script.
- **Go.** `go install` compiles Go code only. A module that embeds the binary of every platform works, but every binary is then committed to Git and downloaded by every user.
- **CRAN.** The repository policy forbids binary executables in source packages, allows a package to download pre-compiled software only as a last resort and with the CRAN team's agreement, and confines user data to `tools::R_user_dir()`.
- **PyPI and conda.** Both carry native binaries per platform as a normal case.
- **Maven Central, NuGet, and Conan.** Each can carry per-platform executables, and each needs its own packaging work.

## Decision

1. **The CLI is distributed through these channels** ([Spec 0012](../specs/0012-workspace-crates-and-cli-distribution.md)):

   | Channel | Package | Mechanism | Also carries | In `v0.1.0` |
   | :--- | :--- | :--- | :--- | :--- |
   | GitHub Releases | one archive per platform | built by cargo-dist | — | yes |
   | crates.io | `playtest-cli` | `cargo install`, a source build | — | yes |
   | PyPI | `playtest-py` | platform wheels built by maturin with `bin` bindings | Python SDK | yes |
   | npm | `@archont561/playtest` and `@archont561/playtest-<platform>-<arch>` | platform packages generated by cargo-npm, listed as `optionalDependencies` of the wrapper package | TypeScript SDK | yes |
   | conda | `playtest` | recipe built with `pixi-build-rust` | — | yes |
   | Go | `github.com/Archont561/playtest/go/cmd/playtest` | download wrapper | Go SDK, in the same module | yes |
   | R | `playtest` | download wrapper `playtest::install_cli()` | R SDK | yes |
   | Conan, Maven Central, NuGet | — | per-platform binary packages | — | deferred |

2. **Nothing downloads at install time.** No package declares an npm lifecycle script, and the R package downloads nothing when it is installed or loaded.
3. **Go and R use a download wrapper in `v0.1.0`.** A wrapper published at version X.Y.Z downloads only the X.Y.Z archive for the host platform from the GitHub Release `vX.Y.Z`, verifies its SHA-256 against the checksum file of that release, keeps the binary in a per-user cache, and runs it. The first run needs network access. The design depends on two conditions:
   - GitHub immutable releases are enabled for the repository, so neither an archive nor its checksum file can be replaced after publication.
   - No Go or R version is published without a binary release of the same version.
4. **The npm wrapper runs Playtest's own loader**, not the shim that cargo-npm generates. The loader finds the platform package, exits with status 3 and a fix when it is missing or not executable, replaces its own process with the binary where the runtime allows it, and otherwise forwards signals and the exit status.
5. **Release archives are `.tar.gz` on Unix and `.zip` on Windows**, each with a SHA-256 file. The Go standard library unpacks both. cargo-dist's Unix default, `.tar.xz`, would need a third-party decompressor in the Go wrapper.
6. **The two-phase rule of ADR 0008 still holds.** Every artifact is built in Phase 1 from the release tag and stored as a workflow artifact. Publishing jobs upload and never compile.
7. **Binary packages for Conan, Maven Central, and NuGet are deferred** until after `v0.1.0`. Java, C#, C, and C++ repositories take the binary from another channel until then.

## Alternatives Rejected

- **cargo-dist's npm installer.** It downloads the binary in `postinstall`.
- **The shim generated by cargo-npm 0.1.5.** In tests under Node 22 it crashed when the wrapper package declared `"type": "module"`, exited with status 1 when the binary was killed by a signal, left the binary running after `SIGTERM`, and printed a stack trace when the platform package was missing.
- **Embedding every platform binary in the Go module.** It works, at the cost of binaries in Git history and in every module download.
- **A checksum written into the wrapper's source.** The wrapper and the binary are built from the same tag, so the checksum does not exist when the wrapper is committed.
- **Downloading the binary while the R package installs.** CRAN policy rules it out.

## Consequences

### Positive
- A user installs the CLI with the package manager the repository already uses.
- No lifecycle script runs, so installs work with Bun and pnpm defaults and in CI that blocks scripts.
- The Python and TypeScript SDKs arrive with the binary, at the same version, in one install.

### Negative
- Releases need a multi-platform build matrix. The Pixi workspace declares only `linux-64` today.
- The Go and R wrappers need network access on first run. A Go or R version without a same-version binary release fails with HTTP 404.
- The integrity of the download wrappers rests on immutable releases, a repository setting that no workflow file can enforce. A repository admin must enable and keep it.
- cargo-npm is young: version 0.1.5, a repository created in March 2026, and one human contributor. Its version must be pinned, and the loader stays in this repository.
- PyPI wheels become platform-specific. A platform without a wheel falls back to the source distribution, which needs Rust 1.88 or newer.
- Java, C#, C, and C++ repositories have no native binary channel in `v0.1.0`.

## Open Questions

1. **Settled (`task_054`):** The supported 5-platform matrix is `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-musl`, `x86_64-apple-darwin`, `aarch64-apple-darwin`, and `x86_64-pc-windows-msvc` ([Spec 0012 §3](../specs/0012-workspace-crates-and-cli-distribution.md)).
2. **Settled (`task_057`):** The receiving conda channel is `https://prefix.dev/archont561/archont561` ([Spec 0012 §4.4](../specs/0012-workspace-crates-and-cli-distribution.md)).
3. **Settled (`task_058`):** `playtest::install_cli()` keeps `Depends: R (>= 4.3.0)`, using `tools::sha256sum()` on R >= 4.5 and a pure base-R FIPS 180-4 SHA-256 fallback on R 4.3–4.4 ([Spec 0012 §5.3](../specs/0012-workspace-crates-and-cli-distribution.md)).
4. CRAN has not reviewed the R wrapper. A download that the user starts by calling a function is a different case from the install-time download that the policy restricts, but acceptance is not confirmed, and the package has not been submitted.
5. **Settled (`task_055`, `task_056`, `task_057`):** npm platform packages repackage the exact Phase 1 `build-cli` binaries via `cargo-npm` `0.1.5`; `maturin` (`build-python`) and `pixi-build-rust` (`build-conda`) compile the same tagged commit in Phase 1 ([Spec 0012 §8](../specs/0012-workspace-crates-and-cli-distribution.md)).
6. Whether Conan, Maven Central, and NuGet later get binary packages. A Conan package built with `export-pkg` and consumed through `tool_requires` worked in a prototype. Per-platform executables on Maven Central (as `com.google.protobuf:protoc` publishes them) and .NET tool packages per runtime identifier were researched but not tested.
