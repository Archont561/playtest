# Milestone M1: Foundation & CLI-First Distribution (`v0.1.0`)

**Status**: In Progress (reopened 2026-11-11)  
**Target SemVer**: `0.1.0`  
**Packages**: crates `playtest`, `playtest-macros`, `playtest-core`, `playtest-assets`, `playtest-cli`; `playtest-py` (PyPI); `@archont561/playtest` and its platform packages (npm); `playtest` (conda); `github.com/Archont561/playtest/go` (Go); `playtest` (R); `Playtest` (NuGet); `io.github.archont561:playtest` (Maven Central); `playtest-cpp` and `playtest-c` (Conan)

> **Why this milestone is open again.** The foundation work (`task_001` to `task_003`) is done and stays done. `v0.1.0` was never tagged or published. [ADR 0015](../adr/0015-cli-first-distribution-and-five-crate-workspace.md) moves the `playtest` CLI from M5 into the first release, so M1 now also delivers the binary, its distribution channels, and the `init` and `sync` commands (`task_050` to `task_059`).

## Objective

Establish the hermetic Pixi monorepo, reserve the package names, configure two-phase trusted publishing, and expose synchronized `VERSION = "0.1.0"` exports in all nine language targets. This part is complete.

Release `v0.1.0` as one version across the CLI and every SDK: split the Rust workspace into five crates, build the `playtest` binary with the embedded SDK files, ship it through the channels of [ADR 0016](../adr/0016-cli-binary-distribution-channels.md), and let a repository pin that version and install the Python and TypeScript SDKs from committed mirrors ([ADR 0017](../adr/0017-committed-sdk-mirrors-and-explicit-wiring.md)). This part is open.

M1 adds no test-framework features. Fixtures, macros, BDD, and property testing start in M2.

### CLI-first distribution (open)

- [ ] **Five-crate workspace** ([Spec 0012 §1](../specs/0012-workspace-crates-and-cli-distribution.md)): `playtest`, `playtest-macros`, `playtest-core`, `playtest-assets`, and `playtest-cli`. A test fails when `playtest` depends on the assets, the CLI, or `clifacet`. The three new crate names are reserved. (`task_050`)
- [ ] **Embedded SDK files** (Spec 0012 §2): `playtest-assets` embeds the published files of every SDK from an explicit list, builds as a packaged crate outside the repository, and a test catches drift from the sources. (`task_051`)
- [ ] **`playtest version` and `playtest init`** ([Spec 0013 §§1, 2, 6](../specs/0013-workspace-configuration-and-sdk-mirrors.md)): `init` writes only `playtest.toml` and `.playtest/`. A binary that does not match the pinned version exits with status 3. (`task_052`)
- [ ] **`playtest sync` and `playtest sync --check`** (Spec 0013 §§3–5): deterministic Python and TypeScript mirrors that a fresh clone installs with uv, npm, pnpm, and Bun, without the CLI and without network access for the SDK. (`task_053`)
- [ ] **Release binaries** (Spec 0012 §3): the platform matrix is declared; each platform gets a `.tar.gz` or `.zip` archive with SHA-256 files on an immutable GitHub Release. (`task_054`)
- [ ] **Registry channels** (Spec 0012 §§4–5):
  - PyPI platform wheels that hold the binary and the Python SDK. (`task_055`)
  - npm platform packages, the wrapper package with the TypeScript SDK, and the loader; no lifecycle script. (`task_056`)
  - A conda package, and `cargo install playtest-cli`. (`task_057`)
  - Go and R download wrappers. (`task_058`)
- [ ] **One version per release** (Spec 0012 §8): a release check rejects any manifest, `VERSION` constant, or embedded SDK version that differs from the release version, and the future of scoped tags is decided. (`task_054`, `task_059`)
- [ ] **`v0.1.0` is tagged and published.** On every channel above, an install followed by `playtest version` prints `0.1.0`.

## Known Gaps in the Existing Release Chain

Found while planning this milestone. None is fixed yet.

- `release-ts` runs `bun pm pack --dry-run`, which writes no tarball, while the `build-typescript` job requires `typescript/*.tgz`. A release that includes TypeScript would stop there. (`task_056`)
- `auto-release.yml` pushes the release tag with the default `GITHUB_TOKEN`. GitHub does not start a workflow for an event that this token causes, so the push is not expected to start `release.yml`. This follows from GitHub's documented rule and was not tested in this repository. (`task_059`)
- Every push to `main` that changes a file outside `backlog/`, `.agents/`, `.devcontainer/`, and the root `*.md` files starts `auto-release.yml`. The repository has no `v*` tag, so `scripts/detect_release.py` compares against the first commit and selects the scope `all`. On 2026-10-23 the run for the merge of pull request #2 decided that a release was needed, and only its failing quality gate stopped it before the tag step. The CI run for the same commit failed at `test-all`. The first such push with passing gates would therefore tag a general release, whether or not this milestone is finished. (`task_059`)
- `Cargo.toml` declares `MIT OR Apache-2.0`, but the repository root has no license file. (`task_054`)
- The root `pixi.toml` allows `rust >=1.82.0`, while building the CLI needs Rust 1.88 or newer. The lock file resolves Rust 1.99.0 today, so the build works, but the bound understates the floor. (`task_050`)
- The Pixi workspace declares only `linux-64`, and every release job runs on `ubuntu-latest`. The release needs every platform of the matrix. (`task_054`)
